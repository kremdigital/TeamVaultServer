# Протокол синхронизации

Документ для разработчиков плагина Obsidian (или других клиентов).

Сервер — это **смесь двух механизмов**:

1. **Метаданные файлов** (создание/удаление/переименование/перемещение, бинарные апдейты) — через журнал операций (`OperationLog`) с vector clock'ом.
2. **Содержимое текстовых файлов** (`.md`) — через **Yjs CRDT**: сервер хранит binary state, клиенты обмениваются update'ами.

## Идентификаторы

- **`clientId`** — стабильный идентификатор инстанса клиента (например, UUID, сохранённый при первом запуске плагина в IndexedDB). Используется как ключ vector clock и как суффикс при разрешении конфликтов имён.
- **`fileId`** — серверный CUID файла, выдаётся при первом `CREATE`. Клиент должен запомнить mapping `vault path ↔ fileId`.
- **`projectId`** — серверный CUID проекта.

## Vector clock

Структура: `Record<clientId, number>`. Сериализуется в JSON.

```ts
type VectorClock = Record<string, number>;
```

Каждый клиент инкрементирует свой счётчик при отправке операции:

```ts
clock[myClientId] = (clock[myClientId] ?? 0) + 1;
sendOperation({ ..., vectorClock: clock });
```

При получении операции от другого клиента:

```ts
for (const [client, counter] of Object.entries(remoteClock)) {
  clock[client] = Math.max(clock[client] ?? 0, counter);
}
```

**Сравнение:**

| Соотношение  | Значение                                  |
| ------------ | ----------------------------------------- |
| `before`     | `a` строго предшествует `b`               |
| `after`      | обратно                                   |
| `equal`      | идентичны                                 |
| `concurrent` | ни одна не предшествует другой — конфликт |

## Подключение

```
WSS /socket.io/
  auth: { apiKey: "osync_<64hex>" }   // плагин / программные клиенты
  // ИЛИ (браузер / веб-редактор):
  //   - cookie `osync_access` (httpOnly) уходит автоматически при
  //     `withCredentials: true` — токен в JS читать не нужно;
  //   - либо явно auth: { token: "<JWT access>" } (fallback, напр. для тестов).
  // Сервер сначала проверяет apiKey, затем сессионный JWT. Права на действия
  // (canViewProject / canEditFiles) проверяются ниже на каждом событии:
  // VIEWER может подключиться и читать, но получит `forbidden` на запись.

→ project:join { projectId, sinceVectorClock?, streamYjs?, skipYjsCatchup? }
← ack {
    ok: true,
    operations: OperationLogRow[],   // упорядочены по createdAt asc
    // Yjs-стейт — ОДИН из двух вариантов:
    yjsDocs?: [{ fileId, sync1: number[], stateVector: number[] }]  // legacy: всё инлайн
    yjsStream?: true, yjsCount?: number                              // новый: стрим (см. ниже)
  }

// Если запрошен streamYjs: после ack сервер стримит доки батчами (по 20):
← yjs:catchup { projectId, docs: [{ fileId, sync1, stateVector }], done: boolean }
```

`sinceVectorClock` — клиент шлёт свой локальный vc. Сервер вернёт операции, чей `OperationLog.vectorClock` имеет хоть в одной координате больше, чем `since`.

`skipYjsCatchup` — клиент вступает в комнату проекта (для op-log catch-up и
live-бродкастов `yjs:update`), но Yjs-доки **не** стримятся вовсе. Ack:
`{ ok, operations, yjsSkipped: true }`. Используется **веб-редактором**: он
открывает по одной заметке и тянет нужный док точечно через `yjs:fetch` (см.
ниже), вместо catch-up всего вальта.

`streamYjs` — клиент просит **не** класть весь Yjs-стейт в ack. Иначе на большом
вальте (сотни текстовых файлов) ack раздувается: сервер грузит все Y.Doc'ы в
память (риск OOM), а клиент применяет всё синхронно и блокирует event-loop →
пропуск Socket.IO heartbeat → reconnect-ливлок. При `streamYjs: true` ack лёгкий
(`yjsStream/yjsCount`), а доки приходят батчами в событиях `yjs:catchup`: сервер
грузит БД по батчу (память ограничена), клиент обрабатывает каждый батч в
отдельном тике (event-loop уступается между сообщениями). Финальный батч —
`done: true`. Старые клиенты не шлют флаг и получают `yjsDocs` инлайн (совместимо).

После catch-up клиент **должен**:

1. Применить операции в порядке от сервера.
2. Для каждого дока (из `yjsDocs` или стримом из `yjs:catchup`) сделать
   `Y.applyUpdate(localDoc[fileId], Uint8Array.from(sync1))` — симметрично
   объединит state; `stateVector` позволяет вычислить обратную дельту (что
   сервер ещё не видел) и дослать её через `yjs:update`.

## Операции (`OperationLog`)

Каждая операция — JSON с типизированным payload:

| `opType` | payload                                                              |
| -------- | -------------------------------------------------------------------- |
| `CREATE` | `{ fileType: 'TEXT' \| 'BINARY', mimeType?, contentHash, size }`     |
| `UPDATE` | `{ fileId, contentHash, size }` (для бинарных; текст идёт через Yjs) |
| `DELETE` | `{ fileId }`                                                         |
| `RENAME` | `{ fileId }` (новый путь — в `OperationLog.newPath`)                 |
| `MOVE`   | `{ fileId }` (новый путь — в `OperationLog.newPath`)                 |

Семантика `RENAME` и `MOVE` на сервере одинакова — оба обновляют `path`. Различие — для семантики на клиенте (например, разные иконки в логе).

### Допустимые пути (обе стороны проверяют)

Путь файла — vault-относительный, через `/`, без ведущего слэша. `normalizeVaultPath`
(`src/lib/files/paths.ts`) отклоняет с `InvalidPathError`:

- абсолютные пути, `NUL`, сегменты `..` и `.`, пустой путь, сегмент длиннее 255 символов;
- зарезервированные **имена папок**, без учёта регистра: `.versions` и `.staging`
  (раскладка хранилища сервера) — всегда; `.obsidian`, `.trash`, `.git` (клиентские
  папки, которых в вальте быть не должно) — только для **входящих** путей;
- имена, которые Windows открывает как **другой** файл (`isWindowsAlias`), — только
  для входящих путей: сегмент с `:` (потоки NTFS: `.obsidian::$INDEX_ALLOCATION` —
  это папка конфигурации) и сегмент вида короткого имени 8.3 — до 8 символов,
  оканчивающихся на `~<цифры>`, с необязательным расширением до 3 символов
  (`OBSIDI~1`, `GIT~1`). Заметка с таким именем не синхронизируется — это цена
  того, что серверу неизвестно, какой короткий псевдоним получила папка на диске
  клиента.

Клиент (плагин с 0.3.8) отклоняет те же имена в **обе стороны** и, кроме того, не
синхронизирует встроенный список служебных файлов ОС, редакторов и других
синхронизаторов (`.DS_Store`, `desktop.ini`, `Thumbs.db`, `.stfolder`, файлы-блокировки
Office и LibreOffice, служебные файлы Dropbox, Google Drive, Nextcloud и т. д.; полный
список — в README плагина, «What is never synced»). Сервер эти имена не запрещает:
они безопасны, просто не нужны в проекте, и старые строки с ними должны оставаться
удаляемыми.

Чтение, листинг (включая фильтр `GET /files?path=`: путь в любом написании, которое
POST сохранил бы так же — `dir//x.md`, `dir\x.md`, `./x.md`, — находит `dir/x.md`, а
отвергнутый гейтом путь даёт пустой список), скачивание и удаление вызывают
`normalizeVaultPath(path, { allowClientDirs: true })`: строка могла попасть в БД до этого запрета, и она должна
остаться читаемой и удаляемой, иначе утёкший `data.json` нечем вычистить, кроме правки
БД. Нестандартное имя папки конфигурации (настройка Obsidian «Override config folder»)
серверу неизвестно — против него работает только клиентский гейт.

Отказ по пути возвращается **машинным кодом**: сокет отвечает `{ ok: false, error:
'invalid_path' }`, REST — `invalid_path`. Клиент обязан считать этот отказ
окончательным и выбрасывать операцию из очереди: текстовое сообщение вида «Reserved
folder name: .trash» классифицировалось как временный сбой, операция возвращалась в
очередь и на каждом реконнекте блокировала отправку всех накопленных правок.

**Клиент обязан проверять пути, которые пришли от сервера, сам.** Сервер и клиент
доверяют друг другу ровно настолько, насколько доверяют друг другу участники проекта:
участник с правом записи мог переименовать свой файл в
`.obsidian/plugins/team-vault/data.json`, и клиент коллеги перенацеливал на этот путь
метаданные, после чего «восстановить на сервере» выгружало чужой `data.json` вместе с
API-ключом (TASK-0027). В плагине этим занимается `checkVaultPath`
(`src/watcher/path-utils.ts`): он отклоняет путь в папке конфигурации (её имя берётся из
`Vault.configDir`, а не зашито), в `.trash`, `.git`, вне папки привязки, а также
абсолютные пути и `..`. Отказ пишется в `sync.log` уровнем `warn` и не прерывает
синхронизацию остальных файлов.

## Разрешение конфликтов на стороне сервера

Сервер делает резолюцию **детерминированно** в момент применения операции (`applyOperation` в `src/lib/sync/operation-log.ts`). Клиент не должен пытаться предотвратить конфликт — просто отправляет свою операцию и обрабатывает `outcome` из ack.

### CREATE-vs-CREATE на одинаковый path

Сценарий: два клиента независимо создают `notes/welcome.md`.

**Resolution:** проигравший по серверному порядку получает путь `<base>.conflict-<clientId>.<ext>`.

```
clientA → CREATE notes/welcome.md
                            ⤷ outcome: { kind: 'created', path: 'notes/welcome.md' }
clientB → CREATE notes/welcome.md     (один и тот же путь, но clientId='B')
                            ⤷ outcome: { kind: 'conflict_create_renamed',
                                          originalPath: 'notes/welcome.md',
                                          finalPath: 'notes/welcome.conflict-B.md' }
```

Клиент B при получении ack должен:

1. На стороне vault создать новый файл `notes/welcome.conflict-B.md` с содержимым своей версии.
2. Удалить локальный `notes/welcome.md` (он уже занят чужой версией).
3. Опционально: показать пользователю диалог «У вас и Алисы конфликтующие версии. Объединить?».

### DELETE > UPDATE

Сценарий: клиент A удаляет файл, клиент B одновременно обновляет.

**Resolution:** DELETE побеждает. UPDATE становится `no_op` с пометкой `suppressed: 'tombstone'` в payload `OperationLog`.

`VaultFile.deletedAt` остаётся выставленным (tombstone), `contentHash` не меняется.

Восстановление возможно — на сервере остаются `FileVersion` snapshot'ы и Yjs-state. Однако автоматический recovery пока не реализован; клиенту следует считать tombstone окончательным удалением.

### CREATE на существующий tombstone (revive)

`CREATE` на путь с tombstone'ом **оживляет** строку (`deletedAt := null`, свежий контент). Это нужно для правомерного пере-создания (пользователь заново добавляет удалённый файл) и для `restore-server` в конфликте DELETE > UPDATE.

«Петля воскрешения» (удалённый файл возвращается с сервера) закрывается **на стороне клиента**, а не отказом сервера от revive:

- **Надёжное удаление** (см. ниже) — файл действительно доходит до сервера как `DELETE` и снимается с диска клиента, поэтому обходить его нечему.
- **`initialPush` уважает серверные tombstone'ы** — перед пушем сверяется с `GET …/files?includeDeleted=true` и **не перезаливает** путь, который сервер считает удалённым (даже если файл ещё лежит на диске). При сбое этого запроса `initialPush` **откладывает** пуш (fail-closed), а не заливает вслепую.
- **Локальное удаление освобождает Y.Doc** и гасит отложенный disk-снапшот, иначе debounce-снапшот после удаления пере-создавал бы `.md` на диске.

> Причинный (vector-clock) revive-guard на сервере прототипировался, но **снят**: он ломал `restore-server` и порождал расхождения (adversarial-ревью). Durable-delete обеспечивается перечисленными клиентскими механизмами.

### Durable delete / очистка tombstone'ов

Soft-delete (`applyDelete`) снимает живые байты и ставит `deletedAt`, но строку `VaultFile` и её операции в `OperationLog` оставляет — иначе `project:join` catch-up переиграл бы `CREATE` заново. Чтобы удаление стало окончательным и не раздувало журнал, есть эндпоинт **`POST /api/projects/:id/purge-tombstones`** (роль ADMIN / владелец / SUPERADMIN):

- тело (опц.) `{ olderThanDays?: number, fileType?: 'TEXT' | 'BINARY' }`; без `olderThanDays` — все tombstone'ы проекта;
- hard-удаляет строки `VaultFile` (каскадом `FileVersion` + `YjsDocument`), их операции в `OperationLog` (по `filePath`/`newPath`) и остаточные байты на диске (`.versions/<fileId>/`);
- ответ — `{ files, operations, versionDirsRemoved }`.

Это же — штатный способ повторить разовую массовую зачистку без ручного SQL.

### Надёжная пропагация удалений (плагин)

Удаление должно дойти до сервера как `DELETE`, иначе файл остаётся live и на catch-up скачивается обратно:

- **Удаление папки:** Obsidian шлёт одно событие на `TFolder` (не по каждому ребёнку), а chokidar `unlink` под залпом ненадёжен. Watcher форвардит folder-delete с меткой `isFolder`, а движок раскрывает его в удаление **каждого** индексированного файла под папкой.
- **Пустой `fileId`:** если путь отсутствует в локальном индексе, `fileId` резолвится из живого списка сервера (`GET …/files`) до отправки; нерезолвимые удаления логируются, а не теряются молча.

### Concurrent RENAME в один target

Сценарий: A переименовывает `a.md` → `target.md`, B одновременно — `b.md` → `target.md`.

**Resolution:** второй RENAME уходит в `target.conflict-<clientId>.<ext>`. Это эквивалентно lex-сравнению clientId'ов (детерминированно).

```
clientA → RENAME a.md → target.md   ⤷ created: target.md
clientB → RENAME b.md → target.md   ⤷ conflict_create_renamed:
                                        originalPath: 'target.md',
                                        finalPath: 'target.conflict-B.md'
```

### REST-записи участвуют в синхронизации

`POST` / `PUT` / `PATCH` / `DELETE` файлов проходят через тот же
`applyOperation`, что и сокетные события. Каждая такая правка:

1. попадает в `OperationLog` → подтягивается клиентом при `project:join`;
2. обновляет `YjsDocument` для текстовых файлов — при `CREATE` его засевает
   сам `applyOperation`, при `UPDATE` документ пересобирается из нового
   содержимого (в сокет-протоколе текст идёт через `yjs:update`, у REST такого
   разделения нет);
3. рассылается подключённым клиентам через мост (см. ниже).

**Псевдоклиент.** У REST-вызова нет `clientId`, поэтому в vector clock
используется `rest:<userId>`: правки одного пользователя через API получают
монотонный счётчик, а плагин видит их как операции ещё одного участника.
Специальной обработки на клиенте не требуется.

**Мост между процессами.** Веб-процесс (:3000) и сокет-процесс (:3001) —
разные процессы без общей памяти. После применения операции веб публикует
уведомление в канал Postgres `team_vault_operation`
(`src/lib/realtime/bridge.ts`), сокет-процесс слушает его и рассылает событие в
комнату проекта (`src/socket/rest-bridge.ts`). В `NOTIFY` уходят **только
идентификаторы** — у него лимит ~8000 байт, поэтому подписчик подгружает строку
журнала из БД сам. Публикация best-effort: её сбой не отменяет уже выполненную
запись, клиент получит операцию при следующем `project:join`.

> До этого REST-записи не попадали ни в журнал, ни в рассылку: правка через MCP
> или веб-загрузку становилась видна плагину только после перезапуска Obsidian
> (через полную сверку `refreshFileIndex`).

### REST-создание на пути удалённого файла

`POST` на путь с тумбстоуном **оживляет** запись — так же, как сокетный
`applyCreate`. Раньше здесь был `409 path_exists` навсегда: уникальный индекс
`@@unique([projectId, path])` покрывает и удалённые строки, поэтому пересоздать
удалённую заметку через REST было невозможно.

Живой файл на пути по-прежнему даёт `409` — см. следующий раздел о том, почему
REST отказывает вместо conflict-rename.

### REST-список файлов: фильтры `path` и `prefix`

`GET /api/projects/:id/files` принимает:

| Параметр         | Действие                                              |
| ---------------- | ----------------------------------------------------- |
| `path`           | ровно одна запись по точному пути (или пустой массив) |
| `prefix`         | поддерево по префиксу пути                            |
| `includeDeleted` | включить тумбстоуны (как и раньше)                    |

Без параметров поведение прежнее — весь проект. `path` идёт по индексу
`@@unique([projectId, path])`.

На несуществующем пути отдаётся **`200` с пустым массивом, а не `404`**: так
вызывающий отличает «нет файла» от «нет проекта», и не ломаются клиенты,
проверяющие отсутствие пути перед созданием (`write_note` в MCP делает именно
это).

### REST-перемещение: конфликт вместо conflict-rename

`PATCH /api/projects/:id/files/:fileId` (используется MCP и внешними клиентами)
ведёт себя **иначе**, чем сокетный `file:rename`/`file:move`, и это намеренно.

|                             | сокет (`RENAME`/`MOVE`)                     | REST (`PATCH`)                              |
| --------------------------- | ------------------------------------------- | ------------------------------------------- |
| путь занят живым файлом     | уводит в `<base>.conflict-<clientId>.<ext>` | **`409 path_exists`**, ничего не меняется   |
| путь занят тумбстоуном      | —                                           | **`409 path_exists`** (как у `POST /files`) |
| перенос на собственный путь | `no_op`                                     | `200`, без изменений                        |

Причина расхождения: conflict-rename рассчитан на офлайн-клиента, который не мог
узнать о занятости пути заранее, и для которого потеря операции хуже лишней
копии. Явный вызов API — обратный случай: клиент хочет либо выполнить операцию,
либо получить внятный отказ, а не обнаружить у себя файл с неожиданным именем.

Порядок внутри `PATCH` важен и закреплён тестами
(`tests/integration/api/file-move.test.ts`): занятость проверяется **до**
обращения к диску, а обновление БД и перенос файла идут одной транзакцией.
`moveProjectFile` — это `rename(2)`, который молча затирает назначение; при
старом порядке (диск → БД) конфликт уничтожал содержимое целевого файла и
оставлял БД рассогласованной с диском.

### Конвенция

Каждый `Y.Doc` имеет один `Y.Text` под ключом `'content'`:

```ts
const doc = new Y.Doc();
const text = doc.getText('content');
text.insert(0, 'Hello');
```

Сервер использует **только** этот ключ для извлечения текста и записи snapshot в `.md` файл.

### Жизненный цикл

```
Plugin local edit                    Server                              Other peers
─────────────────                    ──────                              ───────────
text.insert(...)
  ⤷ doc emits 'update' event (Uint8Array)

socket.emit('yjs:update', {
  projectId, fileId,
  update: Array.from(update)
})
                              ─────► loadYjsDoc(fileId)
                                     Y.applyUpdate(doc, update)
                                     compare state vectors
                                     ⤷ changed = true
                                     upsert YjsDocument {
                                       state, stateVector
                                     }
                                     scheduleSnapshot(5s)
                              ◄───── ack { ok, changed }

                                     // 5s later, after no further edits
                                     persistTextSnapshot()
                                     ⤷ writeProjectFile(.md)
                                     ⤷ recordFileVersion (если хеш новый)

                                     ─────► broadcast 'yjs:update'
                                                                      Y.applyUpdate(localDoc, update)
                                                                      // editor reflects remote change
```

**Важно:**

- Update — **инкрементальный**. Не нужно слать весь state целиком.
- Сервер сам мержит и сам бродкастит. Клиент **не** должен ретранслировать update'ы другим peer'ам напрямую.
- `changed: false` в ack означает, что update не изменил document (например, повторная отправка). Можно безопасно игнорировать.

### Точечная загрузка одного дока (`yjs:fetch`)

Для клиентов, которым нужен лишь один документ (веб-редактор открывает заметки
по одной), есть запрос состояния одного файла без catch-up всего вальта:

```
→ yjs:fetch { projectId, fileId }
← ack { ok: true, sync1: number[], stateVector: number[] }   // как один YjsDocSnapshot
  // или { ok: false, error }  ('forbidden' | 'file_not_found' | ...)
```

Достаточно прав на **чтение** (`canViewProject`) — состояние можно загрузить,
но менять его всё равно только через `yjs:update` (там проверяется
`canEditFiles`). Если Yjs-дока ещё нет, сервер лениво сидит его из `.md` на
диске (как и при catch-up). Клиент применяет `sync1` к локальному `Y.Doc` и
дальше работает как обычно (шлёт `yjs:update`, принимает бродкасты).

> Типовой поток веб-редактора: `project:join { skipYjsCatchup: true }` →
> `yjs:fetch { fileId }` → правки идут `yjs:update`, бродкасты применяются.

**Плагин (≥ 0.3.2) тоже вызывает `yjs:fetch`** — но как точечный ремонт, а
не вместо catch-up: при подключении он по-прежнему делает полный
`project:join`. Запрос уходит для одной текстовой заметки, когда её локальный
док нельзя брать за основу:

- заметку **пропустил catch-up** этой сессии (например, её док ещё грузился
  из IndexedDB);
- у дока есть **припаркованные обновления** — пришли `yjs:update` с дырой в
  истории, и применить их не к чему;
- файл непустой (`size > 0`), а у дока **нет состояния вовсе**.

Без этого живая дельта для такой заметки не доходила до диска до следующего
реконнекта (баг, закрытый в 0.3.2). Клиент применяет `sync1`, затем сверяет
свой док со `stateVector` из ответа и досылает `yjs:update` с операциями,
которых нет у сервера. Таймаут ожидания ack — 15 с; после таймаута плагин
считает, что сервер `yjs:fetch` не знает, и **не повторяет запрос до
следующего подключения**, чтобы каждое сохранение не ждало 15 с заново.

> Совместимость: форму ack (`ok`, `sync1`, `stateVector`, `error`) теперь
> читают два клиента — веб-редактор и плагин. Менять её можно только
> обратно-совместимо.

### История версий как база трёхстороннего слияния (плагин)

С 0.3.2 плагин вливает локальные правки с диска в `Y.Doc` **трёхсторонним**
слиянием, и общий предок для него иногда берётся из истории версий сервера.
Это отдельный контракт, хотя новых эндпоинтов нет:

```
GET /api/projects/:id/files/:fileId/versions              → список, у каждой версии contentHash
GET /api/projects/:id/files/:fileId/versions/:versionId   → байты версии
```

Плагин хранит в своём оплоге `foldedHash` — sha256 последнего содержимого
диска, уже влитого в док. Если нужного текста нет ни в памяти, ни в самом
доке, он ищет в истории версию с `contentHash == foldedHash`, скачивает её,
декодирует как UTF-8 **с сохранением BOM** и **перепроверяет хэш** перед
использованием. Любой промах — версии нет, хэш не сошёлся, ошибка сети —
означает «базы нет», и побеждает содержимое диска (поведение до 0.3.2).
Угаданной базы плагин не берёт никогда: база без текста, который уже есть у
обеих сторон, вставила бы его второй раз, то есть задвоила бы.

Отсюда требования к серверу:

- **`contentHash` версии — sha256 ровно тех байт, что отдаёт download.**
  `recordFileVersion` (`src/lib/files/versioning.ts`) хэш **не считает** —
  он берёт `contentHash` у вызывающего и сохраняет `data` как снапшот. Так что
  инвариант держится на каждом месте вызова: передавай хэш именно этих
  `data`. Нормализация при сохранении версий (окончания строк, BOM,
  завершающий перевод строки) молча сломает поиск базы: хэши перестанут
  совпадать, и слияния тихо откатятся к «побеждает диск», то есть к потере
  несохранённых правок соседа.
- **Текстовые версии должны сохраняться**, когда правки устоялись: именно из
  них плагин восстанавливает базу после перезапуска. Более агрессивная
  чистка истории делает то же самое — меньше слияний с базой, больше
  «побеждает диск».
- Эндпоинты принимают `X-API-Key` и требуют права на чтение проекта
  (`canViewProject`) — как и остальной REST, которым пользуется плагин.

### Восстановление при реконнекте

```
1. socket.connect()
2. socket.emit('project:join', { projectId, sinceVectorClock })
3. По ack:
   3.1. Применить operations[]
   3.2. Для каждого yjsDocs[i]:
        Y.applyUpdate(localDoc[fileId], Uint8Array.from(sync1));
        // Yjs CRDT гарантирует, что мерж коммутативен и идемпотентен
```

После этого локальный документ синхронизирован. Дальше клиент может слать локальные update'ы как обычно.

### Снапшоты `.md` файлов

Сервер периодически (debounced 5s) записывает извлечённый из `Y.Doc` текст в `.md` файл по пути `${STORAGE_PATH}/<projectId>/<file.path>`.

Это нужно для:

- читаемости снаружи (admin может скачать через REST);
- бэкапов FS-уровня (rsync / borgbackup в `${STORAGE_PATH}`);
- истории версий (`FileVersion` snapshot'ы создаются по тому же пути).

## Бинарные файлы

Yjs не используется. **Байты бинарных файлов НЕ передаются по сокету** — на
крупных файлах (раскадровки 10–15 MB) они пробивали `maxHttpBufferSize` и роняли
канал. Вместо этого — **staging через REST + metadata-only socket-операция**:

```
PUT /api/projects/:id/blobs/:hash   (raw body; content-addressed staging)
```

1. Клиент заливает байты в content-addressed staging: `PUT /blobs/:hash` (тело —
   сырые байты; сервер проверяет, что `sha256(body) === :hash`, и кладёт во
   `<projectRoot>/.staging/<hash>`).
2. Затем эмитит **`file:create` / `file:update-binary` БЕЗ поля `data`** (только
   метаданные + `contentHash`).
3. Сервер видит отсутствие `data`, читает staged-блоб по hash с общего диска
   (web- и socket-процессы делят storage volume), применяет операцию
   (`applyOperation` → `OperationLog` → broadcast `file:created` /
   `file:updated-binary`) и удаляет staged-файл. Если блоба нет — ack
   `{ ok:false, error:'blob_not_staged' }`, клиент повторяет.

> Текстовые файлы по-прежнему шлют контент **inline** в `file:create` (он мал и
> нужен серверу для сидирования Yjs-дока). `data` опционально: присутствует для
> TEXT, отсутствует для BINARY.

Пиры скачивают новый файл через `GET /api/projects/:id/files/:fileId`.

**CORS / транспорт плагина.** Бинарные REST-маршруты (`PUT /blobs/:hash`,
`GET /files/:fileId`, `GET …/versions/:versionId`) отдают CORS-заголовки для
origin Obsidian (`app://obsidian.md`) и заголовка `X-API-Key`, чтобы плагин мог
использовать **`fetch`** (стримит большие тела, не блокируя renderer —
в отличие от `requestUrl`, который буферизует всё тело через IPC и не тянет 15 MB).
JSON-запросы плагина остаются на `requestUrl`. Прямые `POST /files` /
`PUT /files/:fileId` сохранены для веб/админки.

## Оффлайн режим (рекомендация для плагина)

```
SQLite local journal:
  table operations(
    op_type, file_id, payload_json, vector_clock_json, status: 'pending' | 'sent' | 'acked'
  )

При локальных изменениях:
  1. Применить локально (на vault).
  2. Inkrement clock[myClientId].
  3. INSERT into operations (status='pending').
  4. Если соединение — emit и ждать ack.
     При ack — UPDATE status='acked'.

При реконнекте:
  1. project:join с sinceVectorClock = последний acked.
  2. Применить server operations.
  3. Replay локальные pending operations (могут получить outcome = 'conflict_create_renamed' — обработать).
```

## Резюме для разработчика

1. Подключайся через `socket.io-client` с `auth.apiKey`.
2. На каждом mount/unmount проекта — `project:join` / `project:leave`.
3. Для текстовых файлов — отправляй Yjs update'ы как `number[]` (Array.from Uint8Array).
4. Для метаданных — посылай `file:create / delete / rename / move` через socket.
5. Для бинарных — `PUT /blobs/:hash` (fetch), затем `file:create` / `file:update-binary` **без `data`**; жди socket-событий от других peer'ов и качай через `GET /files/:fileId`.
6. Каждое `outcome` проверяй: `conflict_create_renamed` означает, что нужно подкорректировать локальный vault.
